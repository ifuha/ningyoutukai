# メッセージ機能(F3: タスク納品補足)の設計メモ

v2.0 の範囲。完了報告にメッセージを付け、報告のあとも担当者とリーダーがやり取りできるようにする。GitHub の PR のコメントに近い形。

表の「区分」の意味は次のとおり。

- **決定**: チームで決まったこと
- **提案**: 私(実装担当)の案。チームの確認がまだ
- **未決定**: 選択肢の段階

## 1. 決まったこと

| 項目 | 区分 | 内容 |
| --- | --- | --- |
| やり取りの履歴 | 決定 | 報告のあとも、担当者とリーダーがメッセージを書き足せる。履歴を持つ |
| 差し戻しと再提出 | 決定 | リーダーは承認のほかに差し戻しができ、担当者は再提出できる |
| 差し戻し中の判別 | 決定 | タスクに**新しいステータス**を持たせて判別する |
| 見える人 | 決定 | 公開しているタスクのコメントは、タスクを見られる人なら誰でも見られる |
| 編集と削除 | 決定 | 今回(v2.0)で実装する |

## 2. 状態(ステータス)

| 値(案) | 画面の表示(案) | 意味 |
| --- | --- | --- |
| `in_progress` | 作業中 | 割り振られた状態。新しいタスクの初期値 |
| `reported` | 確認待ち | 担当者が報告し、リーダーの確認待ち |
| `rejected` | 差し戻し中 | リーダーが差し戻し、担当者の再提出待ち |
| `completed` | 完了 | リーダーが承認した状態 |

### 遷移(区分: 提案)

| 今の状態 | 操作 | 操作できる人 | 次の状態 | メッセージの種類 |
| --- | --- | --- | --- | --- |
| `in_progress` | 報告 | 担当者 | `reported` | `report` |
| `rejected` | 報告(再提出) | 担当者 | `reported` | `resubmit` |
| `reported` | 承認 | リーダー | `completed` | `approve` |
| `reported` | 差し戻し | リーダー | `rejected` | `reject` |

上の表にない操作は 409。`completed` のタスクは、どの操作も受け付けない。実装は `api/src/lib/task-flow.ts`。

### 日時の列の役割

- `reportedAt`: 最後に報告(再提出を含む)した日時。差し戻しても消さない
- `completedAt`: 完了した日時
- 「いまの状態」は `status` だけを見る。日時から状態を推測しない

## 3. 編集と削除(区分: 提案)

| 項目 | 内容 |
| --- | --- |
| 編集できる人 | メッセージを書いた本人だけ(リーダーでも他人のものは編集不可) |
| 編集できるもの | 全種類(`comment` / `report` / `resubmit` / `reject` / `approve`)の本文 |
| 編集の表示 | 編集日時(`editedAt`)を持ち、画面に「編集済み」を出す。編集の履歴は持たない |
| 削除できる人 | 本人、またはリーダー |
| 削除できるもの | 種類が `comment` のものだけ。報告・再提出・差し戻し・承認は、状態の履歴なので消せない |
| 削除の方式 | 論理削除。`deletedAt` を入れ、本文を空にする。履歴には「削除されました」と出る |
| 制限 | 削除済みのメッセージは、編集も再削除もできない。タスクが完了したあとは、編集も削除もできない |

## 4. 見える人と書ける人

| 操作 | 条件 | 区分 |
| --- | --- | --- |
| 履歴を見る | リーダー、担当者、タスクが公開(`isVisible = true`)なら他のメンバーも | 決定(公開の場合)、提案(非公開はリーダーと担当者だけ) |
| コメントを書く | リーダーと担当者だけ。完了後は不可 | 提案 |
| 報告・再提出 | 担当者 | 提案 |
| 承認・差し戻し | リーダー | 提案 |

エラーの返し方は、v1と揃える。

| コード | 条件 |
| --- | --- |
| 404 | プロダクトに所属していない、タスクが見えない、メッセージが存在しない(存在を漏らさない) |
| 403 | 見えるが、その操作をする権限がない |
| 409 | 今の状態ではできない操作(完了後の書き込み、二重の報告、削除済みの編集など) |
| 422 | 入力が不正(本文が長すぎる、差し戻しの本文が空など) |

## 5. データ設計(区分: 提案)

### `tasks` に追加

```typescript
status: text().notNull().default("in_progress").$type<TaskStatus>(),
```

既存データの移行が必須(マイグレーションの末尾に手で足す)。

```sql
ALTER TABLE tasks ADD COLUMN status text NOT NULL DEFAULT 'in_progress';
UPDATE tasks SET status = 'completed' WHERE completed_at IS NOT NULL;
UPDATE tasks SET status = 'reported'
  WHERE completed_at IS NULL AND reported_at IS NOT NULL;
```

### `task_messages` を新規作成

```typescript
export const taskMessages = snakeCase.table(
  "task_messages",
  {
    messageId: uuid().primaryKey().defaultRandom(),
    taskId: uuid()
      .notNull()
      .references(() => tasks.taskId, { onDelete: "cascade" }),
    authorMemberId: uuid()
      .notNull()
      .references(() => productMembers.productMemberId, { onDelete: "cascade" }),
    kind: text().notNull().$type<MessageKind>(), // comment | report | resubmit | reject | approve
    body: text().notNull().default(""),
    createdAt: timestamp().notNull().defaultNow(),
    editedAt: timestamp(), // 編集したら入る
    deletedAt: timestamp(), // 論理削除したら入る
  },
  (table) => [index("task_messages_task_idx").on(table.taskId, table.createdAt)],
);
```

列の型と `snakeCase.table` の書き方は、既存のスキーマに合わせる。

## 6. API(区分: 提案)

パスの前半は、すべて `/api/product/{productId}/task/{taskId}`。

| メソッド・パス | 名称 | 説明 |
| --- | --- | --- |
| **GET** `/message` | メッセージ履歴取得 | 古い順。削除済みは `deleted: true` で本文なし |
| **POST** `/message` | コメント追加 | リーダーと担当者。完了後は 409 |
| **PATCH** `/message/{messageId}` | メッセージ編集 | 本人だけ。本文を変え、`editedAt` を入れる |
| **DELETE** `/message/{messageId}` | メッセージ削除 | `comment` のみ。論理削除 |
| **POST** `/complete-report` (既存を拡張) | タスク完了報告 | 本文は任意。差し戻し中なら再提出として扱う |
| **POST** `/reject` (新規) | タスク差し戻し | リーダー。本文は必須 |
| **PATCH** `/complete` (既存を拡張) | タスク完了確定 | リーダー。本文は任意 |

状態の更新とメッセージの追加は、1つのトランザクションにする。状態の更新は「いまの状態が期待どおりのときだけ」の条件付きにして、同時操作でも二重にならないようにする(外れたら 409)。

### 履歴の応答(例)

```json
{
  "messages": [
    {
      "messageId": "…",
      "kind": "report",
      "body": "実装しました。確認をお願いします",
      "author": { "productMemberId": "…", "userName": "A", "avatarUrl": null },
      "createdAt": "2026-11-01T01:00:00.000Z",
      "editedAt": null,
      "deleted": false
    }
  ]
}
```

## 7. 添付ファイル(区分: 提案。Q10 は未決定)

- v2.0 では、**ファイルの添付は作らない**
- 本文には、URL(GitHub の PR など)を書ける。リンクにするかは画面側で決める
- 理由: ファイルを置く場所(R2 など)と、容量・費用(R13)、アップロードの安全対策が、別の設計になるため。必要になったら v2.1 以降に回す

## 8. 入力の制限(区分: 提案。Q10 は未決定)

| 項目 | 内容 |
| --- | --- |
| 書式 | プレーンテキスト(Markdown は扱わない) |
| 本文の長さ | 最大 2000 文字 |
| 本文が必須のもの | 差し戻し、`comment`(空のコメントは作れない) |
| 本文が任意のもの | 報告、再提出、承認 |
| 前後の空白 | 取り除く。空白だけの本文は、空として扱う |

## 11. v1 の API への影響

| 既存の API | 変更 |
| --- | --- |
| `POST …/task/:taskId/complete-report` | `status` を `reported` に更新する。本文を受け取り、`task_messages` に入れる。差し戻し中なら再提出として扱う |
| `PATCH …/task/:taskId/complete` | `status` を `completed` に更新する。本文は任意 |
| `GET …/tree` | 各タスクに `status` を足す。完了済みを除く条件は、当面 `completedAt` のままでよい |
| 新規タスクの作成 | 変更なし(`status` の初期値は `in_progress`) |
