# v3.1

状態: **下書き(コメント機能の方針を書いた。細部は「決めること」で詰める)**。v3.0 のリリースノートは [../v3.0/release-notes.md](../v3.0/release-notes.md)。

## 1. 目的

画面(ツリー)の上に、**コメント**を足せるようにする。

## 2. 範囲

### 入れるもの

**コメント機能**: 画面(ツリー)にコメントを足せる。

- **権限**: リーダーのみ。作成・編集・削除のすべてで、リーダーの権限が必要
- **必要なエンドポイント**(4 つ)
  - コメントの取得
  - 作成
  - 編集
  - 削除
- **プラグイン(通知)**: コメントをすると、メンバーにメールで知らせる
  - 今回、メールは `api/src/lib/mailer.ts` に分けてあるので、それを使う形になる(下の「決めること」の 6 を参照)

### 入れないもの

(今回は見送るもの。決まったら書く)

## 3. 決まったこと

- コメントを作る・編集する・削除するのは、リーダーだけ(ユーザーの判断)
- エンドポイントは、取得・作成・編集・削除の 4 つ(ユーザーの判断)
- コメントしたら、メンバーにメールで知らせる(ユーザーの判断)

## 4. 決めること

### 4.1 コメントの置き場所と見え方

1. **何に付くか**: ツリー上の座標(メモと同じ `x` / `y`)か、セクションやメンバーのカードに結びつけるか。どれでもよいなら、座標が一番簡単(メモと同じ形)
2. **メモ(付箋)との違い**: メモは、プロダクトの上に置く付箋で、メンバーなら誰でも作れる。コメントは、リーダーだけが書く。両方を残すなら、画面の上での見分け方(色・形)を決める
3. **返信(スレッド)**: ひとつのコメントに、返信を付けるか。付けないなら、1 コメント = 1 つの文章でよい

### 4.2 権限と見える範囲

4. **閲覧**: 取得は、メンバー全員ができるのか、リーダーだけか。書くのはリーダーだけでも、メンバーに読ませる前提なら、取得はメンバーも許す
5. **非公開**: メモのような、公開・非公開の切り替えを付けるか(付けないなら、コメントは常に全員に見える)

### 4.3 メールの通知

6. **仕組み**: v3.0 のメモの公開メール(#226)は、`mailer.send` を、ルートの中から直接呼んでいる(Elysia のプラグインではない)。「ミドルウェア」として `.use()` で差し込む形にするなら、`objectStorage`(`storage-plugin.ts`)や `noteAuthorize` と同じ形のプラグインを新しく作る。**今のまま、ルートから `mailer` を呼ぶ形**でよいか
7. **宛先**: プロダクトのメンバー全員(コメントした本人を除く)でよいか
8. **いつ送るか**: 作成のときだけか、編集のときも送るか
9. **本文**: コメントの内容(何文字まで載せるか)と、プロダクトを開くリンク。メモの公開メールは、200 文字まで
10. **失敗したとき**: 送信に失敗しても、コメントの作成は成功させる(メモの公開メールと同じ)でよいか

### 4.4 データ

11. **保存**: 新しい表(例: `product_comments`)を作る。列は、コメント ID、プロダクト ID(プロダクトの削除で一緒に消える)、作成者(退会したら NULL に戻す)、本文、座標など、作成・更新の日時
12. **削除のしかた**: 消したら実際に消す(物理削除)か、残して隠す(論理削除。メッセージはこちら)か
13. **文字数の上限**: メモは 2000 文字。コメントも同じでよいか
14. **DB の変更**: 表の追加があるので、本番に出す前に `migrate` が要る(リリースの順番は、v3.0 のアイコンのときと同じ)

### 4.5 エンドポイントの形

15. **URL**: 例として、`GET /api/product/:productId/comment`(一覧)、`POST` 同じパス(作成)、`PATCH` / `DELETE` `/api/product/:productId/comment/:commentId`(編集・削除)。メモ(`product-note.ts`)と同じ並びにそろえる
16. **取得の単位**: コメントを、ツリーの取得(`product-tree`)に含めるか、別に取るか

## 6. 作業の分け方

(PR の単位と順番。これまでの流れにならうなら、次の順)

1. api: コメントの表(スキーマ + マイグレーション)
2. api: コメントのエンドポイント(取得・作成・編集・削除。権限のテストを含む)
3. api: 作成時のメールの通知
4. web: 画面(ツリー)にコメントを出す・書く・編集する・消す
5. リリース(`migrate` → `dev`→`main`)
