# v3.1

状態: **下書き(コメント機能の方針が決まった。残りは「決めること」)**。v3.0 のリリースノートは [../v3.0/release-notes.md](../v3.0/release-notes.md)。

## 1. 目的

画面(ツリー)の上に、**コメント**を置けるようにする。リーダーが、メンバーに伝えたいことを、画面の好きな場所に置き、メールでも知らせる。

## 2. 範囲

### 入れるもの

**コメント機能**: 画面(ツリー)の上の好きな場所に、コメントを置ける。

- **メモとの違い**: メモは、**誰でも作れる**付箋で、非公開にして個人のメモとしても使える。コメントは、**リーダーだけが書き**、メンバーに知らせるときに使う。権限と使い方が違う
- **権限**
  - 作成・編集・削除: リーダーだけ
  - 見る: プロダクトの参加者全員(権限は問わない。リーダーもメンバーも見える)
- **置き場所**: ツリー上の座標(メモと同じ `x` / `y`)
- **置き方**(Figma のコメントに近い形): ツールバーで「コメント」を選ぶ → 画面に置く。置き場所は、自分で好きに決める。実装は、ドラッグ&ドロップ
- **必要なエンドポイント**(4 つ): コメントの取得、作成、編集、削除
- **通知(メール)**: コメントを作ると、プロダクトの**メンバー権限の人**にメールで知らせる。**リーダーには送らない**
  - メールの送り方と失敗の扱いは、今の実装に合わせる([4 の 4.2](#42-メールの通知))

## 3. 決まったこと

- コメントを作る・編集する・削除するのは、リーダーだけ(ユーザーの判断)
- コメントを見られるのは、プロダクトの参加者全員(ユーザーの判断)
- エンドポイントは、取得・作成・編集・削除の 4 つ(ユーザーの判断)
- 置き場所は、ツリー上の座標。置き方は、ツールバーでコメントを選ぶ → ドラッグ&ドロップで置く(Figma のコメントに近い形)(ユーザーの判断)
- メモとは、権限と使い方で分ける。メモは個人のメモにも使える。コメントは、リーダーがメンバーに知らせるときに使う(ユーザーの判断)
- メールは、**メンバー権限の人だけ**に送る。リーダーには送らない(ユーザーの判断)
- メールの送り方・失敗の扱いは、**今の実装に合わせる**(ユーザーの判断)

## 4. 決めること

### 4.1 コメントの見え方(画面の設計)

1. **画面の見た目**: 置いたコメントを、画面の上でどう描くか(ピン、吹き出し、本文の見せ方)。Figma のコメントに近い形、という方針までは決まった
2. **ツールバー**: 「コメント」の道具を足す。リーダーにだけ出す(メンバーには出さない)。メモの道具・検索との排他(同時に 2 つ使えない)は、v3.0 の流れにそろえる
3. **メモとの見分け**: 画面の上で、メモとコメントが混ざらないように、色や形を変える
4. **返信(スレッド)**: ひとつのコメントに返信を付けるか。付けないなら、1 コメント = 1 つの文章
5. **移動**: 置いたあとに、ドラッグで動かせるか(メモと同じように、座標の更新を編集に含めるか)

### 4.2 メールの通知

今の実装(v3.0 のメモの公開メール #226、タスクのメールなど)は、**ルートの中から `mailer.send`(`api/src/lib/mailer.ts`)を直接呼ぶ**形です。Elysia のプラグインではありません。コメントも、この形に合わせます。

- **失敗の扱い(他と同じ)**: `mailer.send` は、失敗しても例外を投げません。内部で `console.error("[mailer] …")` を出して、`{ ok: false }` を返します。ルートは、その結果を見ずに、**コメントの作成・編集は成功させます**(メモの公開メール・タスクのメールと同じ)。新しい失敗の処理は足しません
- **宛先**: 「メンバー権限」(`role = 'member'`)の人。リーダーには送らない。**今ある `getMemberContactsExcept` は、リーダーも含む**ので、使えない。メンバー権限だけを取る関数を、`product-access.ts` に足す
- **いつ送るか**: 作成のときに送る。編集のときにも送るか(送るなら、何度も届く)は、決める
- **本文**: コメントの内容(メモの公開メールは 200 文字まで)と、プロダクトを開くリンク
- **宛先が 0 人のとき**: 送らずに終わる(メモと同じ)

### 4.3 データ

6. **保存**: 新しい表(例: `product_comments`)を作る。列は、コメント ID、プロダクト ID(プロダクトの削除で一緒に消える)、作成者(退会したら NULL に戻す)、本文、座標、作成・更新の日時
7. **削除のしかた**: 実際に消す(物理削除)か、残して隠す(論理削除。メッセージはこちら)か
8. **文字数の上限**: メモは 2000 文字。コメントも同じでよいか
9. **DB の変更**: 表の追加があるので、本番に出す前に `migrate` が要る(リリースの順番は、v3.0 のアイコンのときと同じ)

### 4.4 エンドポイントの形

10. **URL**: 例として、`GET /api/product/:productId/comment`(一覧)、`POST` 同じパス(作成)、`PATCH` / `DELETE` `/api/product/:productId/comment/:commentId`(編集・削除)。メモ(`product-note.ts`)と同じ並びにそろえる
11. **権限の書き方**: メモの `noteAuthorize`(`authorize(me).canEdit(note)`)と同じ形で、コメント用の権限(リーダーだけ)を `.use()` で足すか
12. **取得の単位**: コメントを、ツリーの取得(`product-tree`)に含めるか、別に取るか

## 6. 作業の分け方

(PR の単位と順番。これまでの流れにならうなら、次の順)

1. api: コメントの表(スキーマ + マイグレーション)
2. api: コメントのエンドポイント(取得・作成・編集・削除。権限のテストを含む)
3. api: 作成時のメール(メンバー権限だけに送る関数を足す)
4. web: ツールバーの「コメント」と、ドラッグ&ドロップで置く動き。置いたコメントの表示・編集・削除
5. リリース(`migrate` → `dev`→`main`)
