# v3.0 Jev によるタスクの自動割り振り

状態: **案(方針は決定済み。細部は下の「後で決めること」)**。実装は、この文書の承認後に始める。CLI の基本([cli.md](./cli.md))は実装済みなので、その上に足す。

決まったこと(ユーザーの判断):
- 割り振りは **CLI から API を叩いて行う**
- **API が Jev の外部 API を呼び**、その結果でタスクを割り振る(CLI は Jev を直接呼ばない)
- 方式は、タスクごとに「メンバーごとの確率」を Jev に出させ、**確率の高い順に割り振る**
- コマンドの仕様は、この文書の案([2](#2-コマンド案))から始める

## 1. 目的と範囲

リーダーが、プロダクトのタスクを、メンバーに自動で割り振れるようにする。

- 入口は CLI の `assign` コマンド。API は `POST` を 2 つ足す(提案 / 確定)
- Jev(TypeSafe AI の判断モデル)に、「このタスクの担当に向くのは誰か」を聞く。Jev は文章を作らず、**候補ごとの確率**を返す
- 確率の高い順に、メンバーの上限を守りながら割り振る([4.2](#42-割り振りの計算))

### 範囲に入れないこと
- Web 画面の変更(割り振りは CLI だけ。画面は、後で決める)
- 「未割り振り」のタスクを作ること(下の [1.1](#11-この段階では-付け替え-だけ))
- Jev の学習・調整(Jev は渡した情報だけで判断する)

### 1.1 この段階では「付け替え」だけ

今のタスクは、`tasks.product_member_id`(NOT NULL)で、必ず誰かに属している。「誰にも割り振られていないタスク」は、今の DB にはない。さらに、プロダクトとの紐づきも、担当メンバー経由(`tasks → product_members → products`)で持っている。

そのため、この段階の「割り振り」は、**今いる担当者から、Jev が選んだ担当者へ、付け替える**ことにする。スキーマは変えない。

「未割り振り」のタスク(バックログ)を作る案は、**後の段階**に回す。`tasks.product_id` の追加と、`product_member_id` を NULL にできるようにする変更が要り、画面(ツリー・メンバーカード)の全体に影響するため。

## 2. コマンド案

コマンド名は、`cli.md` と同じく**仮**(`ningyoutukai`)。

| コマンド | 内容 |
| --- | --- |
| `ningyoutukai assign --product <名前 or ID>` | 対象のタスクを Jev に判断させ、提案を表示する。確認(y/N)をして、割り振りを確定する |
| `ningyoutukai assign … --dry-run` | 提案を表示するだけ。何も変えない |
| `ningyoutukai assign … --yes` | 確認なしで確定する(スクリプトや AI エージェント向け) |

オプション:
- `--task <ID>`(複数可): 対象のタスクを指定する。省かれたら、プロダクトの**対象の状態のタスクすべて**(下記)
- `--exclude <メンバー>`(複数可): 候補から外すメンバー(名前 or ID。休み中の人など)
- `--max-per-member <N>`: 1 人に割り振る数の上限。既定は `ceil(対象のタスク数 ÷ 候補の人数)`([4.2](#42-割り振りの計算))
- 共通: `--json`、`--api <URL>`、終了コードは [cli.md](./cli.md#2-コマンド案) と同じ(成功 0 / 使い方の誤り 2 / 未ログイン 3 / API エラー 1)

対象のタスクの既定: **リーダーが見られるプロダクトの、`in_progress`(作業中)と `rejected`(差し戻し中)**。`reported`(確認待ち)と `completed`(完了)は、担当を変えると混乱するので入れない。`--task` で明示した場合は、完了済み以外なら対象にする。

出力の例:

```
$ ningyoutukai assign --product 人形使い
Jev の提案(対象 4 件・候補 3 人・モデル jev-1.14.0)

タスク                    今の担当    →  提案        確率    次点
CLI の仕様を書く          伊藤        →  伊藤        0.81    田中 0.12
招待の候補のレビュー      伊藤        →  田中        0.64    佐藤 0.22
README を直す             田中        →  佐藤        0.58    田中 0.31
/device の見た目          佐藤        →  佐藤        0.49    伊藤 0.35

変更されるのは 2 件です(2 件は今のまま)。確定しますか? [y/N]
```

- 「今の担当と同じ」は変更なし(通知もしない)
- 確率が低い提案(**確信度 < 0.5**)には印を付け、`--yes` のときも**割り振らずに**残す(既定のしきい値。下の「後で決めること」)

## 3. API の追加

どちらも**リーダーのみ**(それ以外は 403、プロダクトのメンバーでなければ 404。`create-task.ts` などと同じ)。

| 項目 | 内容 |
| --- | --- |
| `POST /api/product/:productId/task/suggest-assignee` | **提案(何も書き換えない)**。ここで Jev の外部 API を呼ぶ。body: `taskIds?`、`excludeMemberIds?`、`maxPerMember?`。返す: `assignments`(各タスクの現在の担当・提案・確率・確信度・次点)、`model`、`usage` |
| `PATCH /api/product/:productId/task/assignee` | **確定(担当の付け替え)**。body: `assignments: [{ taskId, productMemberId }]`(最大 100 件)。**全件を 1 つのトランザクション**で書き換える |

提案と確定を分ける理由:
- CLI の確認(y/N)をはさめる。`--dry-run` は、提案だけで終わる
- 確定は、**提案をそのまま使わず、API が条件を確かめ直す**: タスクがそのプロダクトに属しているか、新しい担当者がそのプロダクトのメンバーか、完了済みでないか。提案から確定までの間に変わっていても、安全
- Jev の呼び出しは 1 回で済む(確定のときに呼び直さない。呼び出しの料金と、結果のぶれを避ける)

確定のときの副作用(`create-task.ts` と同じ扱い):
- 新しい担当者へ、メールで通知する(`mailer`。失敗してもタスクの付け替えは成功させる)
- 期限があれば、新しい担当者の Google Calendar に登録する(未連携や失敗でも、付け替えは成功させる)。**古い担当者の予定は残る**(`google-calendar.ts` には、予定を追加する関数(`addTaskDeadlineToGoogleCalendar`)しかなく、削除の仕組みがない。消すかは「後で決めること」)
- 担当が変わらないタスクは、書き換えも通知もしない

エラー:

| 状況 | 返すもの |
| --- | --- |
| 候補が 1 人しかいない | 400「候補のメンバーが足りません」 |
| 対象のタスクが 0 件 | 400「対象のタスクがありません」 |
| Jev の API キーが未設定 | 503「自動割り振りは設定されていません」 |
| Jev がエラー・タイムアウト・429 | 502「Jev に接続できませんでした。時間をおいて、もう一度試してください」。**何も書き換えない** |

## 4. Jev の使い方

### 4.1 リクエスト

エンドポイントは `POST https://api.typesafe.ai/v1/systemone`。認証はベアラートークン。**1 回の呼び出しで、全タスクの質問をまとめて送る**(`questions` に、タスクの数だけ入れる)。

Jev の質問の型は、タスクごとに **`choice`**(1 つ選ぶ)を使う。`criteria` に「候補のメンバー」(1〜255 件)を入れると、**全候補の確率(`probabilities`)**と、上位の候補、確信度が返る。「確率の高い順に割り振る」ための材料が、そのまま出る。

```json
{
  "model": "jev-1.14.0",
  "state": {
    "members": {
      "m1": { "openTasks": 3, "recentTasks": ["CLI の仕様を書く", "…"], "role": "leader" },
      "m2": { "openTasks": 1, "recentTasks": ["…"], "role": "member" }
    },
    "tasks": {
      "t1": { "name": "招待の候補のレビュー", "description": "…", "type": "レビュー", "dueInDays": 3 }
    }
  },
  "questions": {
    "t1": {
      "type": "choice",
      "instructions": "タスク t1 の担当に最も向くのは、どのメンバーか。担当中のタスクが少ないメンバー、似たタスクをこなしたメンバーを優先する。",
      "criteria": { "m1": "", "m2": "" }
    }
  }
}
```

- **モデルは版を固定する**(`jev-1.14.0`)。`jev-latest` は別名で、中身が変わると結果が変わるため使わない。版は設定で変えられるようにする
- **メンバーとタスクは、短い別名(`m1`、`t1`)に置き換えて送る。** UUID も、メールアドレスも、氏名も送らない。戻ってきた別名を、サーバーが元の ID に戻す
- 送るのは、割り振りの判断に要る情報だけ: タスクの名前・説明・種類・期限までの日数、メンバーの担当中のタスク数・最近のタスクの名前・ロール。**外部のサービスに送る**ので、リーダーが見られる範囲を超えないようにする(非公開タスクの扱いは、「後で決めること」)
- 1 リクエストの上限は **64k トークン**(`state` と全質問の合計)。超えるときは、タスクを分けて複数回に分ける(上限に近づいたら分割する処理を、最初から入れる)

### 4.2 割り振りの計算

Jev が返した「タスク × メンバー」の確率から、サーバーが割り振りを決める。Jev の呼び出しとは**分けた純粋関数**(`api/src/lib/auto-assign.ts`)にして、単体テストする。

1. すべての「(タスク, メンバー)」の組を、**確率の高い順**に並べる
2. 上から順に見て、**そのタスクがまだ決まっておらず、そのメンバーが上限に達していなければ**、そのタスクをそのメンバーに決める
3. すべて決まるまで続ける

上限(`maxPerMember`)がないと、全タスクが確率の最も高い 1 人に集まることがある。そのため上限を置く(既定は `ceil(タスク数 ÷ 候補の人数)`)。同じ確率のときは、タスク ID の順で決める(結果が毎回同じになるように)。

担当中のタスク数は、Jev に判断材料として渡す(`openTasks`)が、上限の数え方には**入れない**(上限は「今回の割り振りで増える数」だけ)。この扱いは「後で決めること」。

### 4.3 エラー・料金・記録

- 料金は、入力トークンだけ(100 万トークンあたり約 $0.042。出力は無料)。数十件のタスクなら、1 回の呼び出しは 1 円に満たない。応答の `usage.input_tokens` を、ログに残す
- 速度は、1 回数百ミリ秒を想定する。**Workers の CPU 制限(無料枠 10ms)は、外部への待ち時間を数えないので、`fetch` を待つだけなら影響は小さい**。ただし、応答の JSON の処理と、確率の並べ替え(数百〜数千の組)は CPU を使うので、実装後に本番で計測する
- 429 は、`retry-after` に従って**1 回だけ**やり直す。それでも失敗なら 502。タイムアウトは 10 秒
- Jev は**理由を返さない**。あとで「なぜこの人だったか」を調べられるよう、送った `state` の要約・モデルの版・答え(確率)・`usage` を、サーバーのログに残す(個人情報は別名なので入らない)。DB に履歴を持つかは、「後で決めること」

## 5. 設定

| 名前 | 内容 |
| --- | --- |
| `TYPESAFE_API_KEY` | Jev の API キー。**Workers のシークレットと、`.env.local` に置く。リポジトリには入れない** |
| `JEV_MODEL` | モデルの版。既定は `jev-1.14.0` |

- キーの発行と、Workers へのシークレット登録は、**ユーザーが行う**(`wrangler secret put TYPESAFE_API_KEY`)。GitHub Actions の自動デプロイ用のシークレット(`CLOUDFLARE_API_TOKEN` など)も、まだ未登録
- キーが未設定なら、API は 503 を返し、CLI は「自動割り振りは設定されていません」と出す。他の機能には影響しない

## 6. 実装

- `api/src/lib/jev.ts`: Jev の呼び出し(`fetch`)。`mailer` と同じく、**テストでは差し替えられる形**にする(本物の API を叩かない)
- `api/src/lib/auto-assign.ts`: 別名への置き換え、質問の組み立て、割り振りの計算(純粋関数)
- `api/src/routes/task/suggest-assignee.ts`、`api/src/routes/task/assign-assignee.ts`: 上の 2 つの API
- `cli/src/commands/assign.ts`: 提案の表示、確認、確定。API の型は、`tasks-api.ts` と同じく手書き
- テスト:
  - 割り振りの計算: 上限、同じ確率、候補 1 人、全員が上限、確率の取りこぼし
  - Jev の呼び出し: リクエストの形、429 のやり直し、タイムアウト、キー未設定(差し替えて)
  - 提案 API: 権限(リーダーのみ)、他プロダクトのタスクが混ざらない、Jev の失敗で何も書かれない
  - 確定 API: 全件が 1 つのトランザクション、完了済みの拒否、他プロダクトのメンバーの拒否、変更なしは通知しない
  - CLI: 表示、`--dry-run`、`--yes`、確認で `n`

## 7. 作業の分け方(PR の単位)

ブランチ名には `v3` を付ける(例: `feat/v3.0/jev-assign-api`)。`dev` から切って `dev` に PR。

1. **api**: `jev.ts`、`auto-assign.ts`(計算)とテスト
2. **api**: `suggest-assignee`(提案)とテスト
3. **api**: `assignee`(確定。通知・カレンダー)とテスト
4. **cli**: `assign`(`--dry-run` / `--yes`)とテスト
5. **docs**: 使い方、設定(`TYPESAFE_API_KEY`)

本番で使うには、Jev のキーを Workers に登録したあと、api をデプロイする(DB のマイグレーションは要らない)。

## 8. 決めたこと・後で決めること

決めたこと:
- CLI から API を叩き、API が Jev の外部 API を呼んで割り振る
- 確率の高い順に割り振る(上限つき)
- この段階は、**担当の付け替え**だけ(未割り振りのタスクは、後の段階)
- モデルの版は固定し、メンバーとタスクは別名で送る

後で決めること(仮置きで書いてある。レビューで変えられる):
1. **確定のしかた**: 既定は「提案を見せて確認(y/N)」。`--yes` で確認なし。最初から確認なしでよいか
2. **確信度のしきい値**: 0.5 未満は割り振らない、でよいか
3. **担当中のタスク数の扱い**: Jev に判断材料として渡し、上限には入れない、でよいか
4. **非公開タスク**(`isVisible = false`)を、外部の Jev に送ってよいか。送らない(対象から外す)案もある
5. **履歴**: ログだけでよいか。DB に「いつ・誰が・何を提案したか」を持つか
6. **未割り振りのタスク**(バックログ)を、いつ作るか([1.1](#11-この段階では-付け替え-だけ))
7. **画面**: Web に「自動で割り振る」ボタンを足すか
8. **古い担当者の Google Calendar の予定**: 付け替えで消すか
