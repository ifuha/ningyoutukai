# v4.0

状態: **下書き(方針が決まった。細部は「決めること」で詰める)**。前のバージョンのリリースノートは [../v3.1/release-notes.md](../v3.1/release-notes.md)。

## 1. 目的

**人が、AI を「メンバー」として使えるようにする。** 人形使い(人)が、AI の人形(エージェント)にタスクを任せるとき、タスクの説明に収まらない**長い説明を Markdown で渡せる**ようにする。AI の作業の結果は、**人が確認してから**、リーダーへの報告に出す。

背景(考え方): AI が作業を実行できる時代になると、チームの調整の中心は、「作業を人に分ける」ことから、「人と AI に任せて、結果を確認する」ことに移る。確認は、これまでどおり人が行う。

## 2. 範囲

### 入れるもの

#### 2.1 Markdown の文書(R2 に保存して、メンバーに渡す)

- プロダクトに Markdown(`.md`)を保存できる。**保存先は R2**(本文は R2、名前・大きさ・置き場所などは DB)
- 保存した文書を、**メンバー(人も AI も)に渡せる**。**AI が CLI を叩くと、渡された Markdown が返る**
- **メリット**: タスクの説明欄に収まらない長い説明(仕様、手順、守る規則、背景)を、Markdown で書ける
- **R2 のバケットは、アイコン用とは別の、非公開のものを使う。** アイコン用のバケット(`ningyoutukai-product-avatar`)は、公開 URL(`r2.dev`)を有効にしているので、キーが分かれば誰でも読める。文書は、参加者だけが読めればよいので使えない。読み出しは、API を通す(ログインと権限を確かめる)。`wrangler.jsonc` に、2 つ目のバインディングを足す

#### 2.2 ディレクトリ(プロダクトの中のフォルダ)

- プロダクトに、**ディレクトリ**の機能を入れる。Markdown を、ディレクトリに入れて整理する
- **タスクを割り振るとき、ディレクトリ(の Markdown)を、担当のメンバーに渡す**。AI が `pm` でタスクを取ると、そのタスクに結びついた Markdown が一緒に返る

#### 2.3 AI のメンバー(カード)と、AI からの報告

- AI を、人と同じ**メンバーのカード**としてツリーに出す(GitHub のボットのように)
- 作業の流れは人と同じ。分けるのは、**身元**(専用トークン。**持ち主の人**に結びつけ、取り消せる)、**メール**(AI には送らない)、**見た目**(カードに「AI」の印)の 3 か所
- **AI の報告は、そのまま完了報告にならない。** AI が報告を保存すると、まず**下書き**になる。**タスクを持つメンバー(人)が、確認して、「確認報告(完了報告)」に出すかどうかを判断する**。出すと、これまでの流れ(確認待ち → リーダーが確認)に入る
- 完了を確認できるのは、人のリーダーだけ(今の権限のまま)

## 3. 決まったこと

- Markdown は **R2 に保存**し、保存したものを**メンバーに渡せる**。**AI が CLI を叩くと渡される**(ユーザーの判断)
- 長い説明を Markdown で書けることが、狙い(ユーザーの判断)
- プロダクトに**ディレクトリ**の機能を入れ、そこに Markdown を入れる。**割り振るときに、Markdown を渡す**(ユーザーの判断)
- **AI の報告は、タスクを持つメンバーが確認して、「確認報告」に出すかを判断する**(ユーザーの判断)
- AI は、メンバーのカードとして入れる。流れは人と同じにして、身元・メール・見た目の 3 か所だけ分ける(ユーザーの判断)
- 最終確認は、人のリーダーが行う(ユーザーの判断)

## 4. 決めること

### 4.1 Markdown と R2

1. **バケット**: 文書用の非公開バケットを別に作る案でよいか(名前の例: `ningyoutukai-product-docs`)。バインディングの名前(例: `DOCS`)。今のストレージの仕組み(`storage-plugin.ts`)は、バインディングが `STORAGE` の 1 つだけなので、複数に対応させる
2. **キー**: R2 のキーの付け方(例: `<productId>/<documentId>.md`)。ファイル名を変えても、キーは変えない
3. **大きさの上限**: 1 ファイルの上限(アイコンは 1MB)。プロダクトあたりの上限が要るか
4. **版**: 上書きしたときに、前の版を残すか(AI が読んだ版を後で確かめたい場合に要る)。R2 のバージョン管理を使うか、キーに版を含めるか
5. **安全**: 画面で Markdown を描くときは、HTML を禁止する(スクリプトを埋め込まれないように)。ファイルの種類は `.md`(text)に限る

### 4.2 ディレクトリ

6. **構造**: 階層(ディレクトリの中にディレクトリ)を許すか、1 段だけか。1 段なら、実装がずっと小さい
7. **データ**: `product_directories`(名前、親、プロダクト)と、`product_documents`(名前、ディレクトリ、R2 のキー、大きさ、作成者、日時)
8. **作る・直す人**: リーダーだけか、メンバーも書けるか。AI は書けるか
9. **消したとき**: ディレクトリを消すと、中の文書も消すか(R2 の後始末も要る。アイコンの後始末と同じ考え方)

### 4.3 割り振るときの渡し方

10. **結びつけ**: タスクに、(a) ディレクトリを結びつける(中の文書すべてが渡る)か、(b) 文書を個別に選んで結びつけるか
11. **いつ渡るか**: タスクを割り振った時点で、担当のメンバーの「受け取り」に入るのか、担当が取りに来たとき(`pm task <ID>`)に返すだけか
12. **版**: 割り振った時点の版を渡すか、取るときの最新を渡すか
13. **読んだ記録**: AI(と人)が、いつどの文書を取ったかを残すか

### 4.4 AI の報告(下書き → 確認報告)

14. **「タスクを持つメンバー」とは**: (a) タスクの担当が人で、その人が自分の AI に作業させる(AI は担当ではなく、人の道具)のか、(b) AI のメンバーが担当で、その**持ち主の人**が確認するのか。(b) なら、AI のカードに持ち主を結びつけるデータが要る。ここで AI のカードを「担当」にするかどうかが変わる
15. **下書きの持ち方**: 新しい表(例: `task_report_drafts`。タスク、書いた AI、本文、状態 = 未確認 / 採用 / 却下、日時)。本文は DB に置くか、長いものは R2 に置くか
16. **確認の操作**: 担当の人が、(a) 下書きを**そのまま完了報告に出す**、(b) **直してから出す**、(c) **却下**して AI にやり直させる、のどれができるか
17. **既存との関係**: 今の完了報告(`task_messages` の `report`)は、そのまま使う。下書きを「出す」と、`report` のメッセージが 1 件できて、タスクが確認待ちになる
18. **通知**: 下書きが保存されたとき、担当の人にメールで知らせるか(ほかの通知と同じ、ルートから `mailer.send`)

### 4.5 AI のメンバー

19. **データの持ち方**: `product_members` に「種類(人 / AI)」と「持ち主」を足す案。AI のユーザー(`users` の行)を作るか(メールアドレスが要る列があるため)
20. **トークン**: AI 用のトークンを、持ち主が画面で発行する形でよいか。有効期限と取り消し
21. **AI にできること**: 自分に割り振られたタスクの読み書き、渡された文書の取得、下書きの保存だけ。プロダクト全体の変更はできない

### 4.6 CLI

22. **コマンド案**: `pm docs list` / `pm docs get`(文書の取得)、`pm task <ID>` に、結びついた Markdown を含める、`pm report draft`(下書きの保存)、`pm context`(プロダクトの現状 + 渡された文書を、AI に渡す形で出す)
23. **書き込みの解禁**: v3.0 の CLI は読み取りだけ。下書きの保存は書き込みなので、権限の線引き(AI は自分の下書きだけ書ける)を決める

### 4.7 割り振り(Jev)

24. v3.0 の Jev による割り振り(api は実装済み、キー待ち)は、AI のメンバーも候補に入れるか。割り振るときに Markdown を渡す仕組みと、どう組み合わせるか

## 5. 持ち越し(候補)

v4.0 に入れるかは、これから決める。

- Jev による割り振り: API は実装済み。Jev の API キーが未取得のため、本物の Jev は未接続。CLI の `assign` と、通知・カレンダーのフックは未着手(仕様案は [../v3.0/jev-assign.md](../v3.0/jev-assign.md))
- 未割り振りのタスク(バックログ): `tasks.product_member_id` を NULL にできるようにする変更が要る。AI に割り振らせる価値が大きい
- 使われていないコードの整理(テストからしか使われていないコード)

## 6. 作業の分け方

(PR の単位と順番。これまでの流れにならうなら、次の順。細部が決まったら直す)

1. 基盤: 文書用の R2 バケットと、複数のバインディングに対応したストレージ(`storage-plugin.ts`)
2. api: ディレクトリと文書のスキーマ(+ マイグレーション)、エンドポイント(作成・取得・更新・削除)、権限、R2 の後始末
3. api: タスクと文書(ディレクトリ)の結びつけ。割り振るときに渡る
4. api: AI のメンバー(種類・持ち主)と、AI 用のトークン
5. api: AI の報告の下書き(保存、採用 = 完了報告に出す、却下)
6. cli: `docs` / `task` の拡張 / `report draft` / `context`
7. web: ディレクトリと文書の画面、AI のカードの印、下書きを確認して出す画面
8. リリース(`migrate` → R2 のバケットとバインディング → `dev`→`main`)
