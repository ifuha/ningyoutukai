# v4.0

状態: **下書き(方針が決まった。細部は「決めること」で詰める)**。前のバージョンのリリースノートは [../v3.1/release-notes.md](../v3.1/release-notes.md)。

## 1. 目的

**人が、AI を「メンバー」として使えるようにする。** 人形使い(人)が、AI の人形(エージェント)にタスクを任せ、AI からの報告を**プロダクトに残し**、AI に必要な情報(Markdown)を**メンバーに渡せる**ようにする。

背景(考え方): AI が作業を実行できる時代になると、チームの調整の中心は、「作業を人に分ける」ことから、「人と AI に任せて、結果を確認する」ことに移る。最終的な確認は、これまでどおり人が行う。

## 2. 範囲

### 入れるもの

#### 2.1 AI のメンバー(カード)

- AI を、人と同じ**メンバーのカード**としてツリーに出す(GitHub のボットのように、担当者になれる)
- 作業の流れ(担当になる → 作業 → 完了報告 → 確認待ち → リーダーが確認)は、**人と同じ**。分けるのは、次の 3 か所だけ:
  1. **身元**: AI は、専用のトークンで CLI を使う。トークンは**持ち主の人**に結びつけ、持ち主が取り消せる
  2. **メール**: AI にはメールを送らない
  3. **見た目**: カードに「AI」の印を出す
- AI はリーダーにならない。**完了を確認できるのは、人のリーダーだけ**(今の権限のまま)

#### 2.2 AI からの報告を、プロダクトに保存する仕組み

- AI が作業の結果を**報告として保存**でき、プロダクトの参加者が読める
- 本文は Markdown
- 保存は CLI から(AI が使う)。読むのは、画面と CLI
- 既存の完了報告(`task_messages` の `report`)との関係は、「決めること」で詰める

#### 2.3 Markdown をメンバーに渡す仕組み

- プロダクトに Markdown の文書(仕様、作業の指示、守ってほしい規則など)を置き、**メンバー(人も AI も)に渡せる**
- 渡す相手は、プロダクト全体、または特定のメンバー
- CLI で取得できる(AI が、作業の前に読む。`pm context` のような形)

### 入れないもの

(今回は見送るもの。決まったら書く。たとえば、AI の実行そのものをアプリが行うこと、実行回数・費用の上限)

## 3. 決まったこと

- v4.0 の中心は、**AI からの報告を保存する仕組み**と、**Markdown をメンバーに渡す仕組み**(ユーザーの判断)
- AI は、メンバーのカードとして入れる(ユーザーの判断。GitHub のように)
- 作業の流れは人と同じにして、身元・メール・見た目の 3 か所だけ分ける(ユーザーの判断)
- 最終確認は、人のリーダーが行う(ユーザーの判断)

## 4. 決めること

### 4.1 AI のメンバー

1. **データの持ち方**: `product_members` に「種類(人 / AI)」と「持ち主」を足す案。AI のユーザー(`users` の行)を作るか、`users` を介さないか(メールアドレスが要る列があるため)
2. **トークン**: v3.0 の CLI のログインは、人がブラウザで承認する形。AI 用のトークンは、リーダーが画面で発行する形でよいか。有効期限と取り消し
3. **AI にできること**: 自分に割り振られたタスクの読み書き、報告の保存、渡された文書の取得。プロダクト全体の変更はできない
4. **AI の追加**: リーダーだけが追加できるか

### 4.2 AI からの報告

5. **既存との関係**: 今の完了報告は、タスクに紐づく短いメッセージ(`task_messages`、種類 `report`)で、完了の流れに入っている。新しい報告は、(a) これを拡張する(本文を Markdown にして長くする)か、(b) タスクに紐づかない、プロダクト単位の報告として別に持つか
6. **保存する項目**: タイトル、本文(Markdown)、書いた人(メンバー)、関連するタスク(任意)、日時
7. **上限**: 本文の文字数
8. **編集・削除**: 書いた人だけ、またはリーダーも、削除は論理か物理か
9. **読む場所**: 画面のどこに出すか(タスクの詳細、プロダクトの報告の一覧、メンバーのカード)
10. **通知**: 報告が保存されたとき、リーダーにメールで知らせるか(メモ・コメントと同じく、ルートから `mailer.send`。失敗しても保存は成功)

### 4.3 Markdown の文書

11. **データ**: 新しい表(例: `product_documents`)。タイトル、本文(Markdown)、渡す相手(全体 / メンバー指定)、作成者、日時
12. **作る・直す人**: リーダーだけ、でよいか。メンバーも書けるか
13. **渡し方**: 渡された文書を、メンバーがいつ・どう受け取るか(CLI の取得だけか、画面にも出すか)。読んだかどうかの記録は要るか
14. **版**: 直したときに、前の版を残すか(AI が読んだ版を後で確かめられるように)
15. **Markdown の表示**: 画面でどこまで描くか(見出し・リスト・コードまで。HTML は禁止にして安全を守る)

### 4.4 CLI

16. **コマンド案**: `pm report add`(報告を保存)、`pm report list`、`pm docs list` / `pm docs get`(文書の取得)、`pm context`(プロダクトの現状 + 渡された文書を、AI に渡す形で出す)
17. **書き込みの解禁**: v3.0 の CLI は読み取りだけ。報告の保存は書き込みなので、権限の線引き(AI は自分の報告だけ書ける)を決める

### 4.5 割り振り(Jev)

18. v3.0 の Jev による割り振り(api は実装済み、キー待ち)は、AI のメンバーも候補に入れるか。入れる場合、「これは人に、これは AI に」を判断させるか

## 5. 持ち越し(候補)

v4.0 に入れるかは、これから決める。

- Jev による割り振り: API は実装済み。Jev の API キーが未取得のため、本物の Jev は未接続。CLI の `assign` と、通知・カレンダーのフックは未着手(仕様案は [../v3.0/jev-assign.md](../v3.0/jev-assign.md))
- 未割り振りのタスク(バックログ): `tasks.product_member_id` を NULL にできるようにする変更が要る。AI に割り振らせる価値が大きい
- 使われていないコードの整理(テストからしか使われていないコード)

## 6. 作業の分け方

(PR の単位と順番。これまでの流れにならうなら、次の順。細部が決まったら直す)

1. api: AI のメンバー(種類・持ち主)と、AI 用のトークン(スキーマ + マイグレーション、発行・取り消し)
2. api: 報告の保存(スキーマ、エンドポイント、権限、メール)
3. api: Markdown の文書(スキーマ、エンドポイント、権限)
4. cli: `report` / `docs` / `context`
5. web: AI のカードの印、報告を読む画面、文書を置く・渡す画面
6. リリース(`migrate` → `dev`→`main`)
