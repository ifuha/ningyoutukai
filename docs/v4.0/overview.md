# v4.0

状態: **方針が決まった(実装前の仕様)。細部の質問は、実装の PR の中で詰める**。前のバージョンのリリースノートは [../v3.1/release-notes.md](../v3.1/release-notes.md)。

## 1. 目的

**タスクを担当する人が、AI に作業を任せやすくする。** タスクの説明欄に収まらない**長い説明を Markdown で渡せる**ようにし、AI の作業の結果は、**担当者が確認してから**、リーダーへの報告に出す。

背景(考え方): AI が作業を実行できる時代になると、チームの調整の中心は、「作業を人に分ける」ことから、「人と AI に任せて、結果を確認する」ことに移る。確認は、これまでどおり人が行う。

## 2. 範囲

### 入れるもの

#### 2.1 Markdown の文書(R2 に保存して、メンバーに渡す)

- プロダクトに Markdown(`.md`)を保存できる。**保存先は R2**(本文は R2、名前・大きさ・置き場所などは DB)
- 保存した文書を、**メンバーに渡せる**。**AI が CLI を叩くと、渡された Markdown が返る**
- **メリット**: タスクの説明欄に収まらない長い説明(仕様、手順、守る規則、背景)を、Markdown で書ける
- **版を残す**: 文書を直しても、前の内容は残る(版 1、2、3…)
- **要件が変わったら、メールで知らせる**: 文書を直して保存したとき、その文書が**割り振られたメンバー**に、メールで知らせる
- **使われない文書は、自動で削除する**: 長い間呼び出されない文書(**AI も取らず、誰も画面で見ていない文書**)は、古いままで混同のもとになるので、自動で削除する。消したくない文書は、文書ごとに「自動削除しない」に設定できる。削除までの間隔は、自分で決められる。**初期設定は 1 週間**。**自動で削除したら、プロダクトの参加者全員にメールで知らせる**
- **R2 のバケットは、アイコン用とは別の、非公開のものを使う。** アイコン用のバケット(`ningyoutukai-product-avatar`)は、公開 URL(`r2.dev`)を有効にしているので、キーが分かれば誰でも読める。文書は、参加者だけが読めればよいので使えない。読み出しは、API を通す(ログインと権限を確かめる)。`wrangler.jsonc` に、2 つ目のバインディングを足す

#### 2.2 ディレクトリ(プロダクトの中のフォルダ。1 段だけ)

- プロダクトに、**ディレクトリ**の機能を入れる。Markdown を、ディレクトリに入れて整理する
- **階層は 1 段だけ**。ディレクトリの中にディレクトリは作らない(複雑にしすぎない)
- **タスクを作るときに、Markdown を結びつける。結びつけ方は 2 つ**:
  1. **ディレクトリで渡す**: ディレクトリを選ぶと、中の文書すべてが渡る
  2. **文書を個別に渡す**: 文書を 1 つずつ選ぶ
- 両方を同じタスクに付けてもよい。担当者(と、担当者の AI)が、そのタスクを取ると、結びついた Markdown が一緒に返る

#### 2.2a 画面(web)で、Markdown を見る・直す

- **画面で、Markdown の見え方(プレビュー)を確認できる**
- **画面で、文書を編集できる**(新しく作る・直す・消す)。保存すると、新しい版になる(版は残す)
- **ディレクトリのツリーを、画面の右側に出す**(ディレクトリは 1 段)。**スマホでは、ツリーを 1 つのページとして見られる**
- **HTML は書けない**(生の HTML は描かない)
- **同時に編集はできない**: 誰かが編集している間は、ほかの人は編集できない。**編集している人がいる文書には緑の点を出し、編集中の人の名前を出す**
- **ロックは、30 分間、編集(入力)がなければ外れる**。席にいて考えているだけの人には、**ロックが解除されたことを画面で知らせる**。リーダーが強制的に外す操作は作らない

#### 2.2b Markdown の権限(文書だけの権限)

- メンバーにも、**文書の編集権限を渡せる**
- 文書の権限は、**読み取りだけ**の人と、**読み取りと書き込み**の人に分ける
- **この権限は、Markdown(文書)だけの設定**。タスクやプロダクトの権限(リーダー / メンバー)とは別に持つ
- **権限を渡せるのは、リーダーだけ**
- **リーダーは、全権限**(読み取り、書き込み、作成、削除、権限の設定のすべて)
- **何も設定していない場合は、読み取りのみ**(リーダー以外)
- **権限は、ディレクトリごとに付ける**(中の文書すべてに効く)
- **文書は、必ずどれかのディレクトリに入れる**(ディレクトリに入っていない文書は作れない)

#### 2.3 AI の報告は、担当者が確認して出す

- AI は、**担当者(人)の代わりに作業する**。AI は担当者ではなく、**担当者が使う道具**
- AI が作業の結果を保存すると、まず**下書き**になる。**タスクを持つメンバー = 担当者**が、確認して、「**確認報告(完了報告)**」に出すかどうかを判断する。出すと、これまでの流れ(確認待ち → リーダーが確認)に入る
- AI の身元: 担当者が、自分の AI 用のトークンを発行する。トークンは担当者に結びつき、担当者が取り消せる。AI は、その担当者のタスクだけを扱える
- 完了を確認できるのは、人のリーダーだけ(今の権限のまま)

- **AI の報告は、タスクを持つメンバー(= 担当者)が確認して、「確認報告」に出すかを判断する**(ユーザーの判断)

- **権限を出せる(渡せる)のはリーダーだけ。リーダーは全権限。何も設定していない場合は、読み取りのみ**(ユーザーの判断)

- **自動で削除したら、プロダクトの参加者全員にメールで知らせる**(ユーザーの判断)
- **版は残す**(上書きしない)(ユーザーの判断)
- **要件が変わった(文書が直された)ときは、メンバーにメールで知らせる**(ユーザーの判断)
- **「呼び出された」には、AI が CLI / API で取ったときと、人が画面で開いたときの、両方を数える。AI も取らず、誰も見ていない文書を消す**(ユーザーの判断)
- **自動削除の間隔と、「自動削除しない」の設定を変えられるのは、リーダーだけ**(プロダクトの設定の話なので、リーダー権限。ユーザーの判断)
- **削除のごみ箱の機能は付けない**(ユーザーの判断)。消した後に、参加者全員へメールで知らせるのは、決まったとおり
- **ツリーの緑の点と名前は、一定間隔(10〜15 秒)の確認で更新する**。リアルタイム通信は使わない(ユーザーの判断)
- **長い間呼び出されない文書は、自動で削除する**。混同を避けるため(ユーザーの判断)。**自動削除したくない文書は、文書ごとに設定を書き換えて、自動削除しないようにできる**。**削除までの間隔は、自分で決められる。初期設定は 1 週間**(ユーザーの判断)

## 4. 決めること

### 4.1 版(上書きしたとき、前の内容をどうするか)

「版」の話は、**2 つの別の問い**に分かれる。例で説明する。

> 月曜: リーダーが `spec.md`(仕様)を書き、タスクを作って、`spec.md` を結びつける。担当者の AI は、まだ取っていない。
> 火曜: リーダーが `spec.md` を直す(要件が変わった)。
> 水曜: 担当者の AI が `pm task` でタスクを取り、作業を始める。

**問い A: 保存のとき、前の内容を残すか**(質問 1)。**→ 決まった: A2(残す)**。下の A1 / A2 は、選ぶときの説明

- **A1. 残さない(上書き)**: R2 には最新だけがある。簡単で、費用も最小。火曜に直したあと、月曜の内容は戻せない。「AI が何を読んで作業したか」を、後から確かめられない
- **A2. 残す**: 保存のたびに、新しい版(1、2、3…)として別に保存する。R2 のキーに版を含める(例: `<documentId>/v2.md`)か、R2 のバージョン管理を使う。履歴を見られて、戻せる。Markdown は小さい(数十 KB)ので、保存の費用はほとんど増えない。ただし、履歴の画面や、消したときの後始末が要る

**問い B: 渡すとき、どの版を渡すか**(質問 2)。A2 を選んだ場合の話

- **B1. 取るときの最新を渡す**: 水曜に取った AI は、火曜の `spec.md`(v2)を読む。**最新の仕様で作業できる**。ただし、担当者が月曜に見て納得した内容(v1)と、AI が読んだ内容(v2)が違う。担当者は、変更に気づかないかもしれない
- **B2. 割り振った時点の版を渡す**: タスクを作った月曜の版(v1)に固定する。担当者が見た内容と、AI が読む内容が必ず一致する。ただし、火曜の変更(要件が変わったこと)が、AI に届かない。古い仕様で作業してしまう
- **B3. 最新を渡し、取得した版を記録する(私のおすすめ)**: 水曜に v2 を渡し、「この下書きは、`spec.md` の v2 を読んで作った」と記録する。担当者が下書きを確認するとき、「読んだ版」が分かる。タスクを作った後に文書が変わったときは、「タスクを作った後に更新されています」と知らせる。仕様は最新に追いつき、確かめる手がかりも残る

**問い B は、私のおすすめ(B3)のまま進める**(確認済み)。**私のおすすめ**: 問い A は A2(残す。**決まった**)、問い B は B3(最新を渡し、読んだ版を記録する)。v4.0 では、履歴の画面や戻す操作は作らず、**版を残すことと、読んだ版を記録することだけ**にして、後から足せる形にする。A1(上書き)でも動くが、AI が読んだ内容を確かめられなくなるのが弱点。

### 4.1a 自動削除と、変更のメール

(上の「決まったこと」を実現するために、決めること。番号は「自動 1〜」)

- **自動 1. 「呼び出されない」の数え方**: **→ 決まった: CLI / API で取ったときも、人が画面で開いたときも数える**。最後に呼び出された日時(`lastFetchedAt`)を文書に持つ。**一度も呼び出されていない文書**は、作成した日時から数える。画面で開くたびに書き込みが増えるので、更新は間引く(例: 前の更新から 1 時間以内なら、書き込まない)
- **自動 2. 何を消すか**: 文書まるごと(全ての版を含む)を消すか、古い版だけを消して最新は残すか。「混同を避けたい」なら、まるごとが自然。R2 の後始末も要る
- **自動 3. 間隔の持ち方**: 「プロダクトの設定」の話なので、**間隔はプロダクトの設定として持つ**(初期値 7 日)案(私の読み。違えば教えてほしい)。**「自動削除しない」は、文書ごとの印**(`keepForever` など)。プロダクト設定の大きなモーダルに、「文書の自動削除」の項目を足す
- **自動 4. 誰が設定を変えられるか**: **→ 決まった: リーダーだけ**(間隔も、文書ごとの「自動削除しない」も)
- **自動 5. 消す前の知らせ**: **→ 決まった: ごみ箱は付けない**。**消したあとに、参加者全員へメールで知らせる**のも決まった。**消す前のメールは付けない**(聞いていないので、付けない形にした。付けたければ教えてほしい。初期設定が 1 週間と短いので、リーダーが「自動削除しない」を付け忘れると、消えるおそれがある)。消したあとのメールには、文書の名前、消した理由(最後に呼び出された日時)、プロダクトを開くリンクを載せる
- **自動 6. 結びついているタスク**: **未完了のタスクに結びついている文書は、自動で消さない**(私の案。そのまま進める)。編集中の文書も消さない
- **自動 7. 消えた後の記録**: 下書きに「読んだ文書の版」を記録する(B3)ので、文書が消えても、**名前と版の番号だけは残す**(中身は消える)
- **自動 8. 実行のしかた**: 自動削除には、**定期実行**が要る。今の Worker は `fetch` だけで、定期実行の設定がない。Cloudflare Workers の **Cron Trigger**(`wrangler.jsonc` の `triggers.crons`)を足し、`scheduled` を実装する案(例: 1 日 1 回)。ローカル(Bun)では、手動で実行できるスクリプトにする
- **変更のメール 1. 宛先**: **→ 決まった: その文書が割り振られたメンバー**。ディレクトリ経由で割り振られたメンバーも含めるか(含める案)。直した本人は除く
- **変更のメール 2. いつ送るか**: 保存のたびに送ると、誤字の直しでも届く。保存のときに**「メンバーに知らせる」のチェック**を付けて選ぶ案(初期は付ける)。まとめて送る(一定時間内の保存を 1 通にする)案もある
- **変更のメール 3. 本文**: 文書の名前、直した人、版の番号、プロダクト(または文書)を開くリンク。差分(何が変わったか)を載せるか(載せるなら、前の版との比較が要る。最初は載せない案)
- **変更のメール 4. 失敗したとき**: ほかの通知と同じ。送信に失敗しても、保存は成功する

### 4.2 Markdown と R2

1. **版**: 上の 4.1 で決める(問い A)
2. **取得する版**: 上の 4.1 で決める(問い B)
3. **バケット**: 文書用の非公開バケットを別に作る案でよいか(名前の例: `ningyoutukai-product-docs`)。バインディングの名前(例: `DOCS`)。今のストレージの仕組み(`storage-plugin.ts`)は、バインディングが `STORAGE` の 1 つだけなので、複数に対応させる
4. **キー**: R2 のキーの付け方(例: `<productId>/<documentId>/v<版>.md`)。ファイル名を変えても、キーは変えない
5. **大きさの上限**: 1 ファイルの上限(アイコンは 1MB)。プロダクトあたりの上限が要るか
6. **安全**: 画面で Markdown を描くときは、HTML を禁止する(スクリプトを埋め込まれないように)。ファイルの種類は `.md`(text)に限る

### 4.3 ディレクトリと文書

7. **データ**: `product_directories`(名前、プロダクト。階層は 1 段なので、親は持たない)と、`product_documents`(名前、ディレクトリ(**必須**)、現在の版、作成者、日時)。版を残すなら `product_document_versions`(文書、版、R2 のキー、大きさ、日時)
8. **作る・直す人**: **→ 権限の節(4.10)で決める**。メンバーにも編集権限を渡せることは決まった
9. **消したとき**: 文書は必ずディレクトリに入るので、「ディレクトリなしに戻す」はできない。ディレクトリを消すときは、(a) 中の文書も消す(確認を出す)、(b) 中に文書があるディレクトリは消せない(先に文書を消すか、別のディレクトリへ移す)。**(b) の案**。R2 の後始末も要る(アイコンの後始末と同じ考え方)。文書を別のディレクトリへ移せるか(移せる案。権限は移した先のものになる)

### 4.4 タスクとの結びつけ

10. **データ**: タスクと文書の結びつけ(`task_documents`)と、タスクとディレクトリの結びつけ(`task_directories`)。ディレクトリで渡した場合、**後から文書を足したときに、既存のタスクにも渡るか**(渡る方が自然だが、版の問いと同じ話)
11. **タスクの作成画面**: 作成のフォームに、「渡す Markdown」の欄を足す(ディレクトリを選ぶ / 文書を選ぶ)。フォームは詰め込みすぎない形にする(v3.0 のタスクのフォームの反省)
12. **後から変える**: 作ったあとに、結びつけを足す・外すことができるか
13. **読んだ記録**: AI(と人)が、いつどの文書の何版を取ったかを残すか(B3 を選ぶなら、下書きに「読んだ版」を持つ)

### 4.5 AI の報告(下書き → 確認報告)

14. **下書きの持ち方**: 新しい表(例: `task_report_drafts`。タスク、本文、読んだ文書の版、状態 = 未確認 / 採用 / 却下、日時)。本文は DB に置くか、長いものは R2 に置くか
15. **確認の操作**: 担当者が、(a) 下書きを**そのまま完了報告に出す**、(b) **直してから出す**、(c) **却下**して AI にやり直させる、のどれができるか
16. **既存との関係**: 今の完了報告(`task_messages` の `report`)は、そのまま使う。下書きを「出す」と、`report` のメッセージが 1 件できて、タスクが確認待ちになる
17. **通知**: 下書きが保存されたとき、担当者にメールで知らせるか(ほかの通知と同じ、ルートから `mailer.send`。失敗しても保存は成功)

### 4.6 AI の身元

18. **AI のカード**: **→ 私の案で進める: カードとしては出さない**(AI は、担当者が発行したトークンとして存在する。後から、カードに出す形に変えられる)。元の質問: 「AI は担当者が使う道具」という決まりになったので、**AI をツリーのカードとして出す必要があるか**。出さないなら、AI は「担当者が発行したトークン」として存在するだけで、メンバーの表は変えずに済む。出すなら(GitHub のボットのように、誰の AI かをカードに示す)、メンバーに「種類」と「持ち主」を足す。**以前のあなたの言葉(カードとして AI を入れるのはいい)と、今回の決まり(担当者が確認する)が両立する形**を決める
19. **トークン**: 担当者が、自分の AI 用のトークンを画面で発行する形でよいか。有効期限と取り消し。AI にできることは、その担当者のタスクの読み取り、渡された文書の取得、下書きの保存だけ
20. **メール**: AI にはメールを送らない(カードを出す場合)

### 4.7 CLI

21. **コマンド案**: `pm docs list` / `pm docs get`(文書の取得)、`pm task <ID>` に、結びついた Markdown を含める、`pm report draft`(下書きの保存)、`pm context`(プロダクトの現状 + 渡された文書を、AI に渡す形で出す)
22. **書き込みの解禁**: v3.0 の CLI は読み取りだけ。下書きの保存は書き込みなので、権限の線引き(自分の下書きだけ書ける)を決める

### 4.8 割り振り(Jev)

23. v3.0 の Jev による割り振り(api は実装済み、キー待ち)は、タスクの作成と組み合わさる。割り振るときに Markdown を渡す仕組みと、どう組み合わせるか

### 4.10 Markdown の権限

(番号は「権限 1〜」)

決まったこと: 権限は **読み取りだけ** / **読み取りと書き込み** の 2 段階。メンバーにも編集権限を渡せる。**文書だけの設定**。**権限を渡せるのはリーダーだけ**。**リーダーは全権限**。**何も設定していない場合は、読み取りのみ**。**権限は、ディレクトリごとに付ける**。

- **権限 1. 何に付けるか**: **→ 決まった: ディレクトリごと**(中の文書すべてに効く)。文書ごとに上書きする設定は作らない(複雑になるため)。**文書は必ずディレクトリに入れる(決まった)**ので、「ディレクトリに入っていない文書」はない。権限を設定していないディレクトリは、既定(読み取りのみ。リーダーは全権限)になる。プロダクトを作った直後は、ディレクトリが 1 つもないので、最初に作るときに、ディレクトリも作る
- **権限 2. 誰に渡すか**: メンバー個人ごとに付ける(「田中さんは書き込みできる」)。「メンバー全員」にまとめて付ける設定も要るか
- **権限 3. 既定**: **→ 決まった: 何も設定していない場合は、読み取りのみ**。**リーダーは全権限**(決まった)。メンバーに渡されている(割り振られた)文書は、読み取りが必ず付く(元々読み取りが既定なので同じ)
- **権限 4. 誰が権限を変えられるか**: **→ 決まった: リーダーだけ**。書き込みの権限を持つメンバーが、他の人に権限を渡すことはできない
- **権限 5. 作成と削除**: 「書き込み」の権限で、**文書の作成・削除**もできるか。それとも、中身を直すだけで、作成・削除は別か。ディレクトリの作成・削除はリーダーだけ、にする案
- **権限 6. 割り振りとの関係**: 割り振った文書は、**担当者(と、その担当者の AI)に、読み取りを渡す**。AI は読み取りだけ(書き込みの権限は渡さない)にする案
- **権限 7. データ**: `document_permissions`(文書またはディレクトリ、メンバー、権限 = 読み取り / 書き込み)
- **権限 8. API の確認**: 取得は読み取り以上、保存・編集は書き込み、削除は書き込み(または別の権限)。権限の確認は、メモの `noteAuthorize` と同じ形のプラグイン(`.use()`)にそろえる。CLI の取得にも同じ確認が効く

### 4.11 編集ロック(同時に編集できない + 編集中の表示)

決まったこと: 同時に編集はできない。編集中の文書には**緑の点**と、**編集している人の名前**を出す。

- **ロック 1. 持ち方**: 文書ごとに「編集中の人」と「期限」を持つ(例: `document_locks`。文書、メンバー、取った日時、期限)。編集を始める操作で取り、保存・やめるで外す
- **ロック 2. 外れる条件(2 つ)**:
  1. **30 分間、編集がなければ外れる(決まった)**。「編集」は、文字の入力や削除など、文書の内容を変える操作。スクロールやカーソルの移動は、編集に入れない
  2. **ブラウザを閉じた、通信が切れた**ときに、ロックが残り続けないよう、画面が一定間隔(例: 30 秒)で「まだ開いている」と知らせる(ハートビート)。知らせが止まったら、短い期限(例: 90 秒)で外れる(私の案)
  - 1 は、画面の側で最後の編集の時刻を持ち、ハートビートに載せて送る。サーバーは、「最後の編集から 30 分」または「最後の知らせから 90 秒」のどちらかを過ぎたら、ロックを無効とみなす
- **ロック 3. 表示の更新のしかた**: **→ 決まった: 一定間隔の確認(10〜15 秒)**。Worker は常時接続(WebSocket)が難しい(Durable Objects が要る)ので使わない。ツリーを開いている間だけ取る。**リアルタイムではなく、数秒〜十数秒の遅れ**を許す。解除の知らせも、ハートビートの返事で受け取る(サーバーが「ロックは無効です」と返す)
- **ロック 4. ほかの人が開いたとき**: 編集中の文書は、読む(プレビュー)ことはできるが、編集ボタンが押せず、「○○さんが編集中です」と出す。緑の点は、ツリーの文書の横に出す
- **ロック 5. ロックが解除されたとき**: **→ 決まった: 画面で知らせる。リーダーが強制的に外す操作は作らない**。次の細部を決める:
  - **知らせるタイミング**: 解除された瞬間に「ロックが解除されました」と出す。**その前に予告する**: **解除の 1 分前**に「あと 1 分で編集ロックが解除されます」と出す(決まった)。席にいて考えている人が、入力して続ければ、30 分が数え直される
  - **入力中の内容**: 解除されても、画面の入力欄の内容は消さない(手元に残す)
  - **続けて編集したいとき**: 解除後、入力や「続けて編集」で、ロックを取り直す。**だれも取っていなければ、取り直せる**。**ほかの人が先に取っていたら**、取り直せず、「○○さんが編集中です」と出す。この場合、手元の内容は、コピーして残せるようにする(「内容をコピー」のボタン)
  - **保存のときの確認**: 取り直せたときも、保存のときに版番号を確かめる(ほかの人が、その間に保存していたら止める。画面 6)
- **ロック 6. CLI / API での保存**: 画面以外(CLI、AI)から保存するときも、ロックを守る(編集中なら、保存できない)。AI に、文書の書き込みを許すか(許さない案。権限 6)
- **ロック 7. 版との関係**: 保存すると新しい版ができて、ロックを外す。保存せずにやめたときは、版を作らない。念のため、保存のときに版番号を確かめる(画面 6)
- **ロック 8. 緑の点の意味**: 緑の点は、「いま誰かが編集している」ことだけを示す。自分が編集しているときは、別の印(または点なし)にするか
- **ロック 9. 削除との関係**: 編集中の文書は、自動削除の対象から外す(消えるのを避ける)

## 6. 作業の分け方

(PR の単位と順番。これまでの流れにならうなら、次の順。細部が決まったら直す)

1. 基盤: 文書用の R2 バケットと、複数のバインディングに対応したストレージ(`storage-plugin.ts`)
2. api: ディレクトリと文書のスキーマ(+ マイグレーション)、エンドポイント(作成・取得・更新・削除)、権限、R2 の後始末
3. api: タスクと文書・ディレクトリの結びつけ(タスクの作成で渡る)
   - 同じ流れで、版、`lastFetchedAt`、自動削除の設定(間隔、しない)、変更のメール
   - 自動削除の定期実行(Cron Trigger)は、別の PR にする(`wrangler.jsonc` の変更を含み、本番に出す前に動作を確かめたい)
4. api: Markdown の権限(読み取り / 読み取りと書き込み。`.use()` のプラグイン)と、編集ロック(取得・更新・解除、期限)
5. api: AI 用のトークン(担当者が発行・取り消し)
6. api: AI の報告の下書き(保存、採用 = 完了報告に出す、却下)
7. cli: `docs` / `task` の拡張 / `report draft` / `context`
8. web: ディレクトリと文書の画面、タスクの作成フォームの「渡す Markdown」、下書きを確認して出す画面
   - 画面は分けて出す: (a) 右側のディレクトリのツリー(スマホはページ)と、文書のプレビュー(読む)→ (b) 編集・保存(新しい版、変更のメールのチェック)→ (c) 編集中の緑の点と名前(編集ロック)→ (d) 文書の権限の設定 → (e) 前の版の確認 → (f) タスクの作成フォームの「渡す Markdown」→ (g) 下書きを確認して出す画面
9. リリース(`migrate` → R2 のバケットとバインディング → `dev`→`main`)
